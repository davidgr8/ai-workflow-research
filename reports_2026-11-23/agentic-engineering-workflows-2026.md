# Agentic engineering on existing codebases: 2026 field report

**Research cutoff: 23 November 2026.** This report prioritizes first-party accounts of agents doing actual engineering work in 2026, not announcements that a tool is available. A team’s deployment is not necessarily company-wide. Metrics are company-reported and use different denominators; they are not a cross-company productivity ranking. “Not disclosed” means the cited source does not establish the detail, not that the control is absent.

**Sectors considered:**

- Automotive — General Motors
- Aviation — British Airways and Southwest Airlines
- Space systems — NASA Jet Propulsion Laboratory (JPL), F Prime framework
- Logistics, freight, and on-demand delivery — Kuehne+Nagel and Delivery Hero
- Healthcare software — Doctolib
- Media and music streaming — Spotify
- Financial technology and payments — Stripe and Ramp
- E-commerce — Shopify
- Advertising technology — Meta’s ads ranking team
- Mobility and delivery — Grab and Uber, including Grab’s financial-services data workflows
- Developer tools, AI, and cloud infrastructure — GitHub/Microsoft, Anthropic, Google, and OpenAI

## Executive summary

- **Modernize in units that can be checked independently.** Give agents a bounded migration slice and a versioned recipe; compare behavior before cutting over. Compiling and passing the old suite are useful but do not prove compatibility.
- **For everyday engineering, build a path to a reviewable change, not unrestricted autonomy.** Use isolated execution, deterministic scaffolding and checks, and an explicit review or approval policy. Bind evidence to the exact revision that will merge.
- **Make the system legible.** Boot it locally; give agents a short repository map, executable verification commands and relevant runtime artifacts. Use skills for instructions and tools for actions. Neither is a permission boundary.
- **Measure the harness separately from the code.** A historical replay can tell you whether context or a reviewer improved; actual software checks and rollout evidence answer whether the current change is safe to ship.

## Legacy modernization

### GitHub/Microsoft — an in-place TypeScript-to-Rust production port

[Copilot runtime engineering account, 16 Sep 2026; updated 23 Sep](https://github.blog/ai-and-ml/generative-ai/migrating-the-github-copilot-runtime-to-rust-using-copilot/)

- **Architecture and shipment:** Instead of a rewrite branch and big-bang cutover, the team incrementally replaced TypeScript/Node.js slices with Rust behind thin interop shims. The report describes more than 800,000 lines of production Rust, mostly agent-written, and 128 PRs merged and shipped incrementally. Tens of developers also used agents to do ongoing work on the same repository, merging hundreds of PRs per week during the port. This is team-level evidence, not a Microsoft-wide rate.
- **Agent fleet:** A human chose the architecture and decomposed slices. A coordinating session spawned and messaged child sessions with separate branches, worktrees and agent loops; in-session subagents researched or reviewed. The team used a Rust skill, `rust-rebase-review` and an `orchestrate` skill. Worktrees did not prevent a session from reading another session’s files; they were coordination boundaries, not security sandboxes.
- **Verification and gate escapes:** Existing CLI and SDK E2E tests ran throughout; required failures blocked landing. Automated reviewers ran on commits; a merge loop addressed conflicts, review feedback and CI, but the engineer generally stopped it before merge and inspected high-risk changes. A human caught a schema-check bypass that would have hidden an SDK regression. After an agent removed a test for omitted callbacks, the team required explicit consent to change E2E tests. The decisive patterns were shipping small slices and protecting the old behavioral contract, not the number of agents.

### Spotify — streaming, fleet migrations across SQL and Java repositories

[Honk dataset migration, 22 Apr 2026](https://engineering.atspotify.com/2026/4/background-coding-agents-dataset-migrations-honk-part-4) · [Quality at higher velocity, 16 Sep 2026](https://engineering.atspotify.com/2026/9/ai-changed-how-spotify-builds-what-we-learned-and-fixed-about-quality-at-higher-velocity)

- **Scope before editing:** Backstage endpoint lineage identified consumers of two deprecated datasets (~1,800 direct downstream pipelines). Codesearch found in-scope GitHub Enterprise repositories; the Fleetshift plugin orchestrated runs and tracked PRs. Honk, Spotify’s background Claude Code workflow, rolled out 240 automated migration PRs. That is not 1,800 migrated pipelines. Spotify separately reported a Java backend migration completed in three days, without disclosing its Java versions or per-service acceptance tests in that post.
- **Constrain the agent to known mappings:** Human-oriented instructions left too much unstated. The team replaced ambiguous mappings with explicit field tables for dbt and BigQuery Runner. Where semantics depended on a use case, Honk left the field alone and inserted a pointer to guidance. The team dropped Scala/Scio from this automated wave because implementations varied too widely. Honk did not have Claude skills or external MCP schema discovery for this migration; it worked from supplied context.
- **Verification, ownership and consequence:** dbt and BigQuery Runner repos rarely had build-time unit tests, so owning teams manually tested before merge. Spotify’s broader fleet system automatically merges most routine changes after safety checks, but an automated dependency upgrade still passed checks and failed in production; the company did not attribute that incident to agent-authored code. The response included stronger safeguards, more rollback capacity and scheduling automated changes during owners’ working hours. These are two different approval policies, not conflicting descriptions of the same rollout.

### British Airways — aviation, Java service modernization with baseline tests

[AWS account with British Airways engineering and delivery leaders, 16 Nov 2026](https://aws.amazon.com/blogs/devops/how-british-airways-is-accelerating-the-modernization-of-its-java-services/)

- **Before the agent edits:** In a 20-step service-by-service pipeline, GitHub Actions identifies the artifact running in production and inventories dependencies and data sources. Automation uses production traffic logs to size the replacement, and the team runs regression and performance packs against the existing deployment to set a baseline.
- **What the agent changes:** AWS Transform custom upgrades the application to Java 21, replaces legacy framework dependencies and moves deployment from EC2 to ECS on Fargate with AWS Graviton. A separate check looks for remaining hard-coded version numbers. After a build and deployment to a lower environment, the team reruns the same regression and performance packs via the new API gateway route and compares the results with the baseline.
- **Who can ship:** Human code review, security and quality scans, service operations review and cybersecurity approval precede handover and go-live. The account reports an early transformed service in production and wider rollout underway in 2026; over 250 services and roughly 750 repositories describe the target estate, not completed migrations. This is airline business software, not aircraft or flight-control software; agent sandboxing and MCP use are not disclosed.

### Kuehne+Nagel — logistics, containerizing existing RHEL applications

[AWS engineering report co-authored by Kuehne+Nagel’s migration lead, 13 Nov 2026](https://aws.amazon.com/blogs/migration-and-modernization/20-times-faster-kuehnenagel-containerizes-enterprise-apps-in-hours-with-aws-transform/)

- **From source to tested artifacts:** The team connected GitLab repositories and private dependency sources. The AWS Transform containerization agent uses curated skills and templates, traces dependencies, generates application-specific multi-stage Dockerfiles, builds the image and checks that the app starts. It can revise a failed build and retry. Automated scans and validated Helm charts and Kubernetes manifests accompany the image. The documented startup check is a smoke test, not evidence of a full old-vs-new behavioral test suite.
- **Keep the existing release path:** A migration engineer reviews every artifact set against production-readiness and compliance criteria and authorizes promotion. Terraform provisions Amazon EKS, GitLab CI builds and pushes images, and ArgoCD deploys. The team started with four representative apps and completed containerization across all ten in scope. The reported four to eight hours per app refers to containerization, not the entire cloud migration. The account does not specify the agent sandbox or disclose a daily coding workflow.

## Everyday work on existing systems

### Stripe and Ramp — two approaches to financial-technology engineering

- **Stripe Minions: unattended execution, human-reviewed PRs.** Stripe’s [9 Feb 2026 workflow](https://stripe.dev/blog/minions-stripes-one-shot-end-to-end-coding-agents) and [19 Feb implementation notes](https://stripe.dev/blog/minions-stripes-one-shot-end-to-end-coding-agents-part-2) describe Slack/CLI/web entry points and CI-generated flaky-test tickets. A fork of Block’s `goose` runs inside a blueprint that alternates model-driven editing with deterministic Git, lint and test steps. Prewarmed QA devboxes have no production or real customer-data access and restrict egress. The Toolshed MCP catalog then had nearly 500 tools, but a Minion receives a much smaller task-specific set. Fast local checks precede selective CI; after autofixes and at most one agent retry, the branch goes back to the engineer. An engineer inspects the result and requests human review. Stripe reported over 1,300 entirely Minion-written, human-reviewed PRs merged weekly as of the second post—not a current rate or a share of all PRs.
- **Ramp Inspect: collaborative work in a shared session.** In the [12 Jan 2026 architecture](https://builders.ramp.com/post/why-we-built-our-background-agent), OpenCode runs in fresh Modal sandboxes with prebuilt repository snapshots. Cloudflare Durable Objects synchronize session state across Slack, browser and editor. People can steer, edit alongside the agent or stop it, and reviewers can inspect before/after visuals; a PR submitted on the requester's behalf preserves author/approver separation. Ramp’s [27 Oct update](https://ramp.com/blog/introducing-inspect) attributed 74% of merged PRs to Inspect and confirmed human review. The January architecture is a documented snapshot, not evidence that every October session retained the same stack. No universal CI policy was disclosed.

### Shopify — commerce, mobile maintenance with simulator evidence

[River and Aquifer architecture, 28 May 2026](https://shopify.engineering/under-the-river) · [Remote Dev, 22 Oct 2026](https://shopify.engineering/remote-dev)

River handles CI failure investigation, rebases, PR feedback, crash triage and overnight bug fixes that come back ready for review. Aquifer separates append-only Postgres session state, a disposable Go-hosted agent harness and a disposable execution sandbox; a credentials proxy and policy-bearing Nix profiles control tools and environment. For mobile, an agent session gets a prewarmed Mac and iOS Simulator plus Android emulation on a separate Linux VM. River can reproduce a bug, fix it, build and run tests, then replay the same steps and attach before/after recordings. Reviewers can drive the live simulator remotely, not merely read a screenshot the agent selected. Shopify reports River-authored work reaching 61% of merged mobile PRs; this is not company-wide and does not separate routine work from migration work. The posts do not establish a universal merge policy or MCP integration for River.

### Meta — adtech, agents that run ranking experiments

[Ranking Engineer Agent, 17 Mar 2026](https://engineering.fb.com/2026/03/17/developer-tools/ranking-engineer-agent-rea-autonomous-ai-system-accelerating-meta-ads-ranking-innovation/) · [Ads model propagation, 18 Nov 2026](https://engineering.fb.com/2026/11/18/ml-applications/ai-agents-to-scale-ml-innovations-across-ads-ranking-models/) · [Performance-regression agents, 16 Apr 2026](https://engineering.fb.com/2026/04/16/developer-tools/capacity-efficiency-at-meta-how-unified-ai-agents-optimize-performance-at-hyperscale/)

The ads-ranking workflow separates an engineer-guided Planner from an Executor in Meta’s Confucius framework. The Executor runs training jobs, diagnoses failures using runbooks and waits for results; people set compute limits, grant access at preflight and retain strategic decisions. For model improvements, a candidate needs offline gains without guardrail regressions, a statistically significant online A/B win and human approval. Meta estimates agents handled over 60% of technique propagation since March; this is not a measure of all engineering. Separately, FBDetect triggers performance fix PRs for author review using MCP tools for profiling, experiment history, code search and documentation. That is broader infrastructure work, not the Ads workflow, and does not establish the Ads agent’s sandbox or tool permissions.

### Doctolib — healthcare software, remote agents from ticket through post-merge checks

[Anthropic case study with Doctolib’s platform and engineering team, reporting Jan–Sep 2026 results](https://claude.com/customers/doctolib). Headless Claude Code runs via GitHub Actions. From a ticket, remote agents prepare a change, open and maintain the PR and respond to human and agent review comments. After approval, an agent can merge and check the result in production; the affected product team decides whether to accept proposed fixes. The platform team distributes prompts, custom commands and subagents in a shared repo. ### NASA JPL — space systems, agent-assisted maintenance of F Prime

[Cognition’s July 2026 account](https://cognition.com/blog/cognition-doe-genesis-mission) confirms JPL engineers use Devin. The project’s public pull requests show what that means for F Prime, its existing flight-software framework:

- **Review, repair and verification:** In [PR #6083, merged 29 Sep 2026](https://github.com/nasa/fprime/pull/6083), automated review spotted a file-copy defect; Devin wrote the fix and a regression test. The PR records that the new test failed on the unchanged development branch and passed with the fix. It also records 16 passing POSIX tests, including a 1,000-step randomized scenario. A maintainer [approved](https://github.com/nasa/fprime/pull/6083#pullrequestreview-5357717707) and merged the change after CI checks passed.

The PR reports checking its search recipes against 430 framework model files and seven reference repositories. The [project’s AI policy](https://github.com/nasa/fprime/blob/devel/AI_POLICY.md) requires disclosure and makes contributors accountable for reviewing and testing agent output.

### Spotify — Honk beyond a single migration

[Spotify’s engineering platform in use, 3 Jun 2026](https://engineering.atspotify.com/2026/6/code-with-claude-coding-is-no-longer-the-constraint) · [Honk verifier design, 9 Dec 2025; background to the 2026 use](https://engineering.atspotify.com/2025/12/feedback-loops-background-coding-agents-part-3)

The Claude Agent SDK runs in a custom harness on Kubernetes pods; Fleetshift manages scheduling and progress, and trusted tools let Honk run builds in CI. ### Grab — mobility, delivery and financial-services data engineering

[Scarlet production write-up, 23 Nov 2026](https://engineering.grab.com/how-grab-built-scarlet-blog) · [Knowledge-base replays, 23 Nov 2026](https://engineering.grab.com/replaying-merged-changes-knowledge-base-coding-agents-better) · [Palana isolation architecture, 21 Jun 2026](https://engineering.grab.com/part-2-palana-architecture)

- **From request to merge:** Slack, Jira labels or a run API start Scarlet. It posts a visible plan, reasons over the catalog and repo, writes pipeline changes and opens a GitLab merge request. Codex and Cursor can call it as a tool. The agent cannot approve or merge; catalog or scheduler writes wait for explicit approval. Data-platform calls use short-lived requester credentials; GitLab writes are attributable to the bot. LangGraph interrupts checkpoint a run while the requester signs in.
- **Tools and architecture:** Versioned Markdown skills cover routing, repositories, platforms and workflows. The runtime pins an immutable skill bundle. Internal platforms sit behind MCP bridges that list operations and load schemas on demand. A migration that passed CI but failed at runtime led Grab to use deterministic scaffolds and contract validation for predictable job configuration, leaving column mapping and transformations to the model.
- **Correctness:** CI produces candidate tables in an isolated environment and a manifest tied to the commit. Scarlet compares output against current production tables: types, keys, duplicates, row counts, null distributions, numeric summaries and row-level differences. Mandatory checks depend on the change; inconclusive fails, and a new commit invalidates the verdict. Post-merge verification and automated revert proposals were described as future work. Grab reports the updated workflow was in production from May, with the MR merge rate rising from about 50% in May to over 85% in September; this is not a defect-rate measure.
- **A different sort of test:** For backend agent context, Grab extracts entry points, configuration and call graphs deterministically from syntax trees; subagents summarize that structure, a verifier checks batches, and owners approve knowledge MRs. On 50 historical MRs, paired agents planned from pre-merge worktrees with or without the skill. An LLM grader saw the shipped diff; the agents did not. The results measure planning, not runnable code, and the shipped diff is only one valid solution. Material knowledge changes are gated on replays. The separate [Grab Bench evaluation, 12 Aug 2026](https://engineering.grab.com/grab-bench-evaluating-ai) scores coding tasks using visible and hidden tests, maintainability, efficiency and hard failure gates; Grab describes a patch that passed visible tests but missed a hidden stateful invariant.
- **Sandboxing:** Separately, Grab documents Palana, a production Kubernetes platform for agents: per-user/per-agent namespaces, default-deny Cilium network policies, proxy/OPA egress checks and Vault-backed proxy-only credentials. Not every secret is proxy-only. The Scarlet post documents an isolated candidate-data environment and split identities; it does not say Scarlet uses Palana.

### Google — multi-agent search for Borg improvements

[Google Research, 13 Nov 2026](https://research.google/blog/advancing-science-engineering-with-antigravitys-teamwork-feature/). Antigravity’s `/teamwork` routes tasks to declared coordination patterns: agents receive limited task context, independent critics challenge candidates, and unmodified tests or hardware counters provide feedback. Humans define constraints and retain final acceptance. For tightly coupled code the team found sequential stages more useful than parallel work; `/boost` packages a sequential implementation and verification loop. Two changes to Borg scheduling shipped and reduced TPU preemption by 24% on some hardware while preserving SLOs and utilization. The post also shows validated rewrite experiments (Rust Zircon passed kernel tests and booted on arm64; libgav1 reached bit-exact conformance-suite parity), not evidence the rewrites shipped. Task context restriction is not OS isolation; the Borg account does not disclose its sandbox policy or tool permissions.

### Anthropic — maintaining Claude Code

[Code-review workflow, 15 Oct 2026](https://claude.dev/blog/solving-code-review-at-anthropic/) · [Verification practices, 16 Nov 2026](https://claude.dev/blog/how-the-claude-code-team-thinks-about-verification/)

- **Daily workflow:** Claude runs the build, tests and linter before opening a PR. Repository-local `verify` skills tell it how to boot, drive and inspect the actual application. The team advocates black-box E2E smoke tests, property tests for invariants and differential tests for migrations; these are recommendations as well as examples, not a claim that every change runs all three. Team-specific checks include verifying that old transcripts still load when session schemas change.
- **Review and authority:** Parallel bug-finding agents generate candidates; verifier agents vote on findings; a separate security pass and unresolved findings can block merge. A classifier assigns zero, one or two human approvals depending on risk; some paths always need a person. Persistently failing checks escalate to a human after three rounds. A merge queue reruns checks on current main plus the change; flags, internal use and staggered release provide additional checkpoints.
- **Protect the verifier:** `REVIEW.md` is read from the base branch, not the PR being judged. Verification is recorded at commit level. A new commit check can run in observe mode before enforcing. Historical incidents and reverts form positive examples for review evaluations; stable merged changes are controls, and tuning and fixed evaluation sets are separate. An agent vote is not proof of correctness; the system also relies on executable checks, owner rules and staged rollout.

### Transferable architecture, not a legacy case: OpenAI’s Codex harness

[Harness engineering, 11 Feb 2026](https://openai.com/index/harness-engineering/). OpenAI reports using Codex CLI with GPT‑5 to build and operate an internal product starting from an **empty repository**. This is evidence for harness design, not for brownfield migration. A short `AGENTS.md` points to versioned docs; domain layers have dependency directions enforced by custom linters and structural tests. ## What to adopt in an existing codebase

The following is a proposed rollout, not a claim that any one company uses the whole design. Start with one service and one repeatable change class; expand only when approval and verification can keep up.

### Track A: Legacy migration

1. **Inventory before changing code.** Use source analysis and dependency/consumer maps to identify owners, interfaces and affected jobs. Keep the old executable available as a behavioral reference. Agree which quirks are contract and which are intentional changes.
2. **Build an acceptance harness first.** Characterize high-value legacy behavior with black-box API, UI, CLI or batch fixtures. Add focused unit tests for risky conversions and integration tests across storage, queues, auth or SDK boundaries. Compare old and new on the same normalized fixtures or approved, privacy-preserving traffic samples. Use property tests for invariants and performance budgets for latency/resource regressions. Keep approved differences explicit; “same output” is not required where the change is intentional.
3. **Choose a migration seam.** Use an adapter/interop shim for a runtime port, or versioned endpoints and per-consumer PRs for a data migration. Give the agent one module or consumer at a time, using codemods/templates for routine structure and an agent for ambiguous mappings. Tell it when to stop and ask. Sample across different frameworks before dispatching a fleet.
4. **Release in reversible waves.** Have owners approve scope and parity exceptions. Re-run checks on the merge result, shadow or canary the new path where feasible, compare telemetry, and keep a rollback path. Do not grant a fleet worker its own cutover authority. For embedded or safety-related changes, add whatever traceability, target-hardware/simulator validation and independent sign-off your lifecycle requires; the public GM case does not show these controls.

### Track B: Everyday implementation

1. **Make work repeatable.** Provide short repo instructions linked to versioned design decisions and owner maps; expose one fast `verify` command or skill. Give it a seeded app it can boot per change. Favor consistent module layouts and enforce dependencies mechanically instead of rewriting the architecture just to accommodate an agent.
2. **Separate action from authority.** Use a deterministic scheduler or state machine for steps, budgets, retries and approval pauses. Run each task in an ephemeral container or VM suited to its trust level. A branch or worktree is not a sandbox. Deny network access by default, broker scoped credentials outside the model process, and prevent access to customer data or production writes by default. Run generated scripts in that same constrained environment; promote useful scripts to a reviewed recipe rather than treating one-off generated code as infrastructure.
3. **Use the simplest useful tool surface.** Skills explain when and how; CLI tools and scripts fit local operations; MCP fits discoverable services with typed calls. Put permissions and argument validation in the gateway or tool implementation, not the instructions. Use a single worker until there is a clear reason to split—parallelize independent slices or use separate reviewers with fresh context and bounded scope. A deterministic CI gate or an owner, not a supervisor model, has the final word.
4. **Make evidence a deliverable.** The agent PR should carry the task, what changed, checks run with the commit SHA, results and uncertainty. Run cheap unit/build/lint checks first, then relevant integration or black-box tests in CI. Protect tests, CI and approval rules against unreviewed changes by the agent. Keep high-impact paths owner-gated; consider auto-merge only for a well-defined low-risk class after an observe-only trial.
5. **Measure quality, not just adoption.** Use paired historical replays to assess prompts, skills and reviewers, and keep a separate fixed evaluation set. Track first-pass CI, false-positive review burden, human review time, escaped defects, reverts, rollback time and cost per accepted change. Compare against a pre-rollout baseline and keep watch on review queues and PR size as throughput increases.
