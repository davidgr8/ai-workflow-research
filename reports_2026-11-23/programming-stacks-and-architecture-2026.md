# Programming stacks and architecture for agentic engineering: 2026

**Research cutoff: 23 November 2026.** This report covers the general software stack: what teams build and port, what makes a codebase easier for agents to change, and where code, execution, data, and models live. See the [engineering case studies](agentic-engineering-workflows-2026.md) for individual workflows and the [AI tooling catalog](agentic-ai-developer-tools-2026.md) for agent SDKs and integrations.

## What is actually moving

- **TypeScript and Python have the strongest broad growth signal.** [GitHub’s 2026 Octoverse](https://github.blog/news-insights/octoverse/octoverse-commits-pushes-reach-new-highs-in-2026-as-developers-build-with-agents/) ranks TypeScript, Python and JavaScript first through third by contributors. From September 2025 to September 2026, TypeScript added 3.62 million monthly contributors and Python added 3.23 million. TypeScript was the primary language in **35%** of new GitHub repositories with a detected agent signal, versus **24%** without one. A signal includes events such as agent-opened PRs; repositories without a detected signal may still use agents. This is an association, not a controlled productivity comparison.
- **Rust is growing and is a demonstrated target for systems ports, not a default replacement for backend and web stacks.** Octoverse reports that Rust’s contributor community doubled, the fastest percentage growth among its top languages. That and the ports below do not establish an industry-wide migration from C++, JavaScript or Java.
- **Established stacks are still substantial.** In the [2026 Stack Overflow Technology survey](https://survey.stackoverflow.co/2026/technology), 62% of respondents to the language question selected JavaScript, 58% Python, 44% TypeScript, 28% Java and 27% C#. Among respondents to the database question, 58% selected PostgreSQL and 42% SQLite. These are separate, multiple-choice respondent samples. They are not deployment shares or measurements restricted to agentic repositories. The frameworks below are practical fits, not a framework market-share ranking.
- **The clearest architecture shift in the cases is around execution, not application topology.** Teams isolate short-lived agent workers from durable tasks and credentials, and make more of the application runnable and verifiable from a checkout. That works with a modular monolith, an existing service estate, or a local client backed by cloud workers. The reviewed sources do not show a broad shift to peer-to-peer applications or a wholesale reversal of microservices.

## Where AI-assisted ports actually ended up

| 2026 case | Source → target | What justified or verified the move | Status |
| --- | --- | --- | --- |
| [GitHub Copilot runtime](https://github.blog/ai-and-ml/generative-ai/migrating-the-github-copilot-runtime-to-rust-using-copilot/) | TypeScript on Node.js/V8 → Rust with C ABI embedding for SDK consumers | Reduce startup and memory overhead and avoid requiring a separate CLI process for SDK integration. Thin interop seams let the team replace pieces incrementally; existing CLI and SDK end-to-end tests protected the contract. | **Shipped incrementally**; 128 PRs merged and shipped. This was a runtime with explicit embedding needs, not a whole-product move away from TypeScript. |
| [Google Zircon and libgav1 experiments](https://research.google/blog/advancing-science-engineering-with-antigravitys-teamwork-feature/) | C++ → Rust for a microkernel and an AV1 decoder | Zircon passed kernel unit tests and booted on ARM64; libgav1 matched the conformance suite bit for bit. Keeping the old suite unchanged gave the agents an external verification target. | **Validated experiments**; not evidence the Rust versions shipped. The same post separately reports shipped Borg scheduler improvements, not a Borg language rewrite. |
| [British Airways Java services](https://aws.amazon.com/blogs/devops/how-british-airways-is-accelerating-the-modernization-of-its-java-services/) | Older Java dependencies and EC2 deployments → Java 21 and ECS/Fargate on Graviton | Modernize runtime and deployment without changing language. Reuse regression and performance packs against old and new deployments. | **First transformed service live**; estate-wide rollout is not complete in the account. |
| [Spotify data migration](https://engineering.atspotify.com/2026/4/background-coding-agents-dataset-migrations-honk-part-4) | Deprecated datasets → replacement datasets in existing SQL-based dbt and BigQuery Runner pipelines | Explicit field maps and consistent pipeline shapes made fleet edits tractable. More variable Scala/Scio implementations were left outside this automated wave. | **240 automated migration PRs**; not a Scala-to-SQL port or proof every consumer migrated. |
| [Kuehne+Nagel](https://aws.amazon.com/blogs/migration-and-modernization/20-times-faster-kuehnenagel-containerizes-enterprise-apps-in-hours-with-aws-transform/) | Existing RHEL applications → Docker images and Helm/Kubernetes workloads on Amazon EKS | Keep application code and dependencies where possible; generate packaging, verify builds and startup, then promote through existing GitLab CI and Argo CD. | **All ten in scope containerized**; startup validation is not behavioral parity or a count of production cutovers. |

The sample illustrates three distinct moves: **language port, runtime upgrade, and repackaging**. Start with the smallest one that addresses the measured problem. [GM’s 2026 account](https://github.com/customer-stories/general-motors) describes documenting COBOL and Fortran before modernization but does not identify the target languages or verify individual cutovers, so it is not evidence for a particular destination.

## Which stacks fit which work?

| Work | General-purpose stack | Why it helps an agent, and where it stops |
| --- | --- | --- |
| Web UI and product APIs | [TypeScript](https://www.typescriptlang.org/tsconfig/#strict) on [Node.js](https://nodejs.org/en/about/previous-releases); [React/Next.js](https://nextjs.org/docs) for a full-stack app, or React + [Vite](https://vite.dev/guide/) for a frontend with a separate API | Use strict type checking, one lockfile per workspace, schema validation at network boundaries, and [Playwright](https://playwright.dev/) smoke tests. Shared types make refactors easier to check, but erased TypeScript types do not validate incoming JSON or UI behavior. Pick the build setup that matches the deployment, not the one with more scaffolding. |
| Data work, model integration and APIs | Python with [FastAPI](https://fastapi.tiangolo.com/), [Pydantic](https://docs.pydantic.dev/), [uv](https://docs.astral.sh/uv/), [Ruff](https://docs.astral.sh/ruff/), [pytest](https://docs.pytest.org/) and a type checker | Define data contracts explicitly, lock dependencies, and give agents a fresh environment with a fast verification command. Keep notebooks for exploration; move repeatable transformations into importable modules and test them on fixed datasets. GitHub’s [ecosystem analysis](https://github.blog/news-insights/octoverse/what-the-fastest-growing-tools-reveal-about-how-software-is-being-built/) specifically calls out Python’s move beyond notebooks and interest in uv. |
| Existing enterprise APIs and jobs | Java with [Spring Boot](https://docs.spring.io/spring-boot/) and Maven/Gradle; C# with [ASP.NET Core](https://learn.microsoft.com/en-us/aspnet/core/) and `dotnet test` | Keep existing conventions, integration tests, and dependency tooling. [Testcontainers](https://testcontainers.com/) can exercise a real database or queue against seeded fixtures. Both stacks give precise build errors and stable seams. This is a good default for healthy Java/.NET estates, not evidence of mass migration to either framework. |
| Portable workers, control planes and infrastructure CLIs | [Go](https://go.dev/doc/) for networked services and simple binaries; [Rust](https://doc.rust-lang.org/cargo/) where memory, startup, native embedding or predictable resource usage justify it | Use `go test` or `cargo test`, plus race checks, fuzzing or benchmarks where relevant. Shopify’s agent runtime is a [concrete Go example](https://shopify.engineering/under-the-river); GitHub’s port is a Rust example. Compiler feedback narrows the search space but cannot prove protocol compatibility, performance or safe FFI. |
| SQL and analytics pipelines | SQL with [dbt](https://docs.getdbt.com/); PostgreSQL for transactional state, warehouse-native SQL for batch data | Give the agent schemas, lineage and fixtures. Check keys, nulls, row counts and output diffs as well as whether SQL compiles. [Grab compares candidate tables to production](https://engineering.grab.com/how-grab-built-scarlet-blog); the comparison is tied to the candidate commit. |

**The useful comparison is between feedback loops, not just languages.** A well-instrumented existing service with a reproducible build, a seeded database and a contract suite is usually a better first target than a statically typed rewrite that lacks a test oracle. Make formatting, type checks, dependency rules and focused tests fast enough to use while editing. Preserve at least one end-to-end check of behavior that neither the agent nor its implementation branch can silently redefine.

## Architectural patterns: what is changing and what is not

| Pattern | Evidence and practical implication |
| --- | --- |
| **Modular monolith or layered application** | [OpenAI’s greenfield harness case](https://openai.com/index/harness-engineering/) enforces dependency direction within each domain with custom linters and structural tests. This supports **mechanically enforced modules**, not a claim that the project used a particular deployment topology. For an existing example of the pattern outside agent-specific evidence, see [Shopify’s modular monolith work](https://shopify.engineering/deconstructing-monolith-designing-software-maximizes-developer-productivity). Start with package boundaries or tools such as [Spring Modulith](https://spring.io/projects/spring-modulith/) before introducing a network boundary solely for AI. |
| **Service-oriented systems and microservices** | [British Airways](https://aws.amazon.com/blogs/devops/how-british-airways-is-accelerating-the-modernization-of-its-java-services/) modernizes one existing service at a time; [Spotify](https://engineering.atspotify.com/2026/4/background-coding-agents-dataset-migrations-honk-part-4) uses lineage, repository discovery and explicit mappings across a fleet. Independent releases and owners make changes easier to scope; cross-service contracts, environment setup and partial outages make them harder to verify. Use versioned API/event schemas and consumer contracts. Do not split a service solely to give an agent a smaller prompt. |
| **Thin client, durable control plane, ephemeral execution** | [Shopify Aquifer](https://shopify.engineering/under-the-river) keeps session history in an append-only PostgreSQL log and makes the agent process and sandbox disposable. [Ramp Inspect](https://builders.ramp.com/post/why-we-built-our-background-agent) syncs Slack/browser/editor sessions with Cloudflare Durable Objects and executes in Modal sandboxes. Store task state and artifact references outside the worker; resume from durable state rather than granting a long-lived process broad credentials. |
| **Async jobs with explicit checkpoints** | [Grab Scarlet](https://engineering.grab.com/how-grab-built-scarlet-blog) pauses a run while the requester signs in and resumes from a checkpoint. Apply the same pattern with a job table or durable queue for long-running tests, approvals and retries. Make callbacks idempotent and tie test results to the exact commit. A queue is useful when runs outlive requests; it does not require a microservice per workflow step. |
| **Reproducible environments as part of the repository** | [OpenAI](https://openai.com/index/harness-engineering/) can boot the app per Git worktree; [Shopify Remote Dev](https://shopify.engineering/remote-dev) provides a remotely accessible mobile-simulator setup. For services, start with [Docker Compose](https://docs.docker.com/compose/) or Testcontainers, seeded fixtures and a one-command smoke test. Use [OpenTelemetry](https://opentelemetry.io/docs/) or local logs to make failures inspectable. A worktree is a checkout boundary, not a sandbox. |
| **Local-first and peer-to-peer** | These solve different problems. [SQLite](https://sqlite.org/whentouse.html) is a reasonable local store for a single-user desktop tool or offline dev cache; sync only when required. [Automerge](https://automerge.org/) is an option for multi-writer offline collaboration where conflict resolution is a product requirement. Local-first does not imply peer-to-peer transport, and none of the cases above demonstrates P2P becoming a default for engineering agents. Centralized policy, audit and approval can still coexist with offline client data. |

## Where should data, workers and models run?

Choose independently where **source and fixtures**, **worker execution**, **durable task state**, and **inference** live. A local terminal can send code to a hosted model; a cloud sandbox can keep production data out; a self-hosted worker can still call a third-party API. None of those labels alone answers the data-governance question.

| Deployment choice | Useful when | Concrete technology and limit |
| --- | --- | --- |
| Local execution, hosted model | An engineer wants immediate interaction with a checkout and local test suite. | Put the worker in a restricted container or VM when it will run untrusted code; provide synthetic fixtures and scoped credentials. Track what prompts, code and logs leave the machine. Local execution is not local inference. |
| Managed cloud workers | You need burst capacity, reproducible images, a browser/simulator, or asynchronous jobs. | [Ramp’s Modal setup](https://builders.ramp.com/post/why-we-built-our-background-agent) is a documented example. For normal app workloads, [British Airways’ ECS/Fargate deployment](https://aws.amazon.com/blogs/devops/how-british-airways-is-accelerating-the-modernization-of-its-java-services/) shows that managed containers are also an alternative to running Kubernetes yourself. Keep credential injection and artifact retention explicit. |
| Organization-controlled infrastructure or private cloud | You must control network paths, identities, workspaces and data access, or already operate an internal platform. | [Grab’s Palana](https://engineering.grab.com/part-2-palana-architecture) uses Kubernetes, default-deny Cilium policies, an OPA-checked egress proxy and Vault-backed credentials. If using Kubernetes, policy and sandbox design—not namespace naming alone—provide isolation. Owning the platform increases operational burden. |
| Local or self-hosted inference | Code cannot be sent to a model vendor, offline work is needed, or a measured workload justifies owning GPU capacity. | [llama.cpp](https://github.com/ggml-org/llama.cpp) is a local inference option; [vLLM](https://docs.vllm.ai/en/latest/) and [SGLang](https://docs.sglang.io/) serve models on your infrastructure. All three appear in GitHub’s 2026 open-source project data, which signals developer interest, not hosting market share. Benchmark quality on actual repository tasks, latency, hardware cost and model-license constraints. |

**A good first build:** Keep the existing application architecture. Pick one isolated workflow and expose `setup`, `test` and a smoke check from a fresh checkout. Use PostgreSQL for shared task state if needed, SQLite for single-user state, and store logs and test artifacts separately from prompts and credentials. Add a queue or dedicated worker when work outlives a request; change languages or split services only when you can name the constraint, measure the old behavior, and verify the new one.
